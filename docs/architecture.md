# Архитектура и проектные решения

## 1. Основные сценарии

**Клиент**
1. Открывает Mini App из бота → сервер проверяет `initData` → создаётся/находится профиль.
2. Выбирает услугу → дату (14 дней, доступность считает сервер) → свободное время.
3. На подтверждении указывает телефон (если ещё не указан) → подтверждает.
4. Сервер повторно проверяет все правила, сохраняет запись в транзакции, ставит в очередь подтверждение, уведомление массажисту и напоминания за 24 и 2 часа.
5. В «Мои записи» видит предстоящие, историю и отменённые; отменяет или переносит запись не позднее чем за 6 часов.

**Массажист (администратор)**
1. Открывает тот же Mini App → сервер видит роль `admin` → открывается панель управления.
2. Смотрит расписание по дням, неделям и месяцам, фильтрует по статусу, открывает карточку записи.
3. Создаёт запись вручную (в том числе для клиента без Telegram), переносит, отменяет, отмечает «визит состоялся» или «неявка».
4. Настраивает недельный график (несколько интервалов в день), разовые исключения, услуги и правила записи.
5. Получает уведомления о новых записях, отменах и переносах клиентами.

## 2. Компоненты

```
Telegram ──► Бот (aiogram 3, long polling) ──┐
   │                                          │  PostgreSQL 16
   └─► Mini App (React, nginx) ──/api──► API (FastAPI) ───┤  (единственный источник данных)
                                                          │
                       Обработчик уведомлений (app.worker) ┘ ──► Telegram Bot API
```

| Процесс | Команда | Назначение |
|---|---|---|
| `api` | `uvicorn app.main:app` | REST API `/api/v1`, авторизация, бизнес-правила |
| `bot` | `python -m app.bot` | `/start`, `/book`, `/mybookings`, `/help`, кнопка Mini App, отметка «пользователь запускал бота» |
| `worker` | `python -m app.worker` | отправка уведомлений из очереди `notification_jobs`, повторы |
| `web` | nginx | статика Mini App и проксирование `/api` на backend |
| `db` | PostgreSQL 16 | данные, ограничения целостности, очередь задач |

## 3. Схема базы данных

| Таблица | Ключевые поля и ограничения |
|---|---|
| `users` | `id` UUID, `telegram_id` BIGINT UNIQUE (NULL у клиентов, добавленных вручную), `name`, `phone` (E.164), `role` ENUM(client, admin), `is_active`, `allows_write_to_pm`, `bot_started_at`, `bot_blocked`, `notifications_enabled`, `admin_notes` |
| `services` | `name`, `description`, `duration_minutes` (5–720), `price_minor` (копейки), `currency`, `buffer_minutes` (NULL = общий буфер; задел на индивидуальный), `is_active`, `sort_order` |
| `appointments` | снимки `service_name_snapshot`, `duration_minutes`, `price_minor_snapshot`, `currency_snapshot`; `starts_at`, `ends_at`, `buffer_minutes`, `blocked_until` (TIMESTAMPTZ); `status` ENUM; `cancelled_at`, `cancelled_by`, `created_by`, `comment`, `idempotency_key`. **EXCLUDE USING gist (tstzrange(starts_at, blocked_until) WITH &&) WHERE status = 'booked'**; UNIQUE(`client_id`, `idempotency_key`) |
| `appointment_history` | действие, автор и роль, старое/новое время, старый/новый статус, детали JSONB |

| `notification_jobs` | `appointment_id`, `recipient_telegram_id`, `notification_type`, `dedup_key`, `payload`, `scheduled_at`, `status`, `attempts`, `sent_at`, `last_error`; UNIQUE(`dedup_key`, `recipient_telegram_id`) |

## 4. Алгоритм расчёта слотов

Реализация: `backend/app/services/availability.py`.

1. Дата интерпретируется в часовом поясе массажиста (`settings.timezone`).
2. Базовые интервалы — строки `working_hours` для дня недели. Если день отмечен нерабочим — интервалов нет.
3. Добавляются исключения `open`, затем вычитаются `closed` и `break`.
4. Кандидаты начала генерируются от начала каждого интервала с шагом `slot_step_minutes` (30).
5. Окончание услуги = начало + длительность услуги; кандидат отбрасывается, если услуга не укладывается в интервал.
6. Интервал блокировки = `[начало, начало + длительность + буфер)`.
7. Кандидат отбрасывается, если интервал блокировки пересекается с блокировкой любой активной (`booked`) записи.
8. Отбрасываются кандидаты раньше `now + min_lead_minutes` (по умолчанию 60 минут).
9. Даты вне горизонта (сегодня + 13 дней = 14 календарных дней в часовом поясе массажиста) не возвращаются.

Пример ТЗ: запись 10:00–11:00 блокирует 10:00–11:10, поэтому 10:30 и 11:00 недоступны, 11:30 доступно.

## 5. Защита от двойного бронирования

* Предварительная проверка: при создании и переносе сервер заново рассчитывает слоты и проверяет, что выбранное время — допустимый свободный кандидат. Цена, длительность и статус берутся только с сервера.
* Окончательная гарантия — exclusion constraint PostgreSQL `ex_appointments_no_overlap`. При параллельных транзакциях вторая получает ошибку ограничения, которая превращается в `409 Conflict` с кодом `slot_taken`. Отменённые/завершённые записи в ограничение не попадают.
* Перенос — `UPDATE` той же строки в одной транзакции (с `SELECT … FOR UPDATE`). Если новый интервал занят, транзакция откатывается и исходная запись остаётся без изменений.
* Повторная отправка: клиент передаёт заголовок `Idempotency-Key`; повтор с тем же ключом возвращает уже созданную запись (`200`), уникальный индекс защищает и от гонки повторов.
* Тесты: `test_concurrent_booking_same_slot_service_level` (12 потоков), `test_concurrent_booking_via_api` (8 параллельных HTTP-запросов), `test_database_constraint_blocks_overlap_directly`.

## 6. Уведомления

* Задачи создаются в той же транзакции, что и изменение записи (`notification_jobs`), поэтому не теряются при перезапуске и не создаются для неудавшихся операций.
* Дедупликация — уникальный ключ `(dedup_key, recipient)`, вставка `ON CONFLICT DO NOTHING`. Для напоминаний ключ включает время визита: после переноса создаются новые напоминания, старые помечаются `cancelled`.
* Напоминание не создаётся, если до визита осталось меньше соответствующего срока; перед отправкой проверяется, что запись всё ещё активна и время не изменилось.
* Обработчик берёт задачи `FOR UPDATE SKIP LOCKED`, каждая — отдельная транзакция. Временные ошибки — до 5 попыток с экспоненциальной задержкой; `RetryAfter` от Telegram переносит задачу без расхода попытки; блокировка бота пользователем — задача `failed`, пользователь помечается `bot_blocked`.
* Сообщения отправляются только тем, кто разрешил боту писать (`allows_write_to_pm` в initData) или запускал бота (`/start`); остальным задача помечается `skipped`.
* Темп отправки ~20 сообщений/с — ниже ограничения Bot API.

## 7. Авторизация и безопасность

* `POST /auth/telegram` принимает исходную строку `initData`, проверяет HMAC-SHA256 по официальному алгоритму (ключ `HMAC("WebAppData", BOT_TOKEN)`), срок `auth_date` (24 ч) и только после этого создаёт/находит пользователя по Telegram ID.
* Сервер выдаёт сессионный токен (HMAC-подпись `SECRET_KEY`, 24 ч). Роль в токене не хранится — читается из БД на каждый запрос.
* Роль администратора даётся только через `ADMIN_TELEGRAM_IDS` или `python -m app.cli create-admin`.
* Чужие записи возвращают `404` (не раскрываем факт существования).
* Ограничение частоты запросов, единый формат ошибок, ORM без сырых SQL-строк с пользовательскими данными, логи без телефонов и токенов.

## 8. Допущения (принятые простые и безопасные решения)

1. Буфер может выходить за конец рабочего интервала: последний сеанс 18:00–19:00 при окончании работы в 19:00 допустим.
2. Шаг слотов отсчитывается от начала каждого рабочего интервала (10:00, 10:30, … ; после перерыва — от его окончания).
3. Минимальный срок до визита по умолчанию — 60 минут (в ТЗ параметр упомянут без значения; меняется в настройках, 0 — выключено).
4. Ограничение 3 активных будущих записи на клиента — защита от занятия всего расписания одним пользователем (меняется в настройках).
5. Перенос клиентом подчиняется тому же 6-часовому правилу, что и отмена; при переносе используются длительность и буфер из снимка записи.
6. Стоимость услуги по умолчанию — 0 («по договорённости»), пока массажист её не задаст.
7. Администратор может создавать и переносить записи вне графика (переключатель «вручную»), но пересечения запрещены и для него.
8. «Визит состоялся» и «Неявка» доступны только после начала визита; автоматического проставления статусов нет.
9. Тумблер «Напоминания» в профиле отключает только напоминания; подтверждения, отмены и переносы приходят всегда.
10. Ограничение частоты запросов хранится в памяти процесса API — достаточно для одного сервера; при горизонтальном масштабировании нужен общий лимитер (nginx/Redis).
